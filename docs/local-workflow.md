# The local workflow, step by step

Actors: **you** at the dashboard of the **controller** `ameise`, one **planner** agent per topic and one **worker** agent per issue. Beside them act the **reviewer panel**, the pull request's author session, GitHub **CI**, and **Codex** as external PR reviewer. The controller drives every stage; the plugins carry the prompts ([ADR 0056](adr/0056-the-controller-replaces-the-orchestrator-and-runs-every-local-session-headless.md), [ADR 0063](adr/0063-plugins-are-skills-and-agents.md)). The [controller's readme](../controller/README.md) is the reference for each step.

| Step | Who | What happens | Done when |
| --- | --- | --- | --- |
| Plan | you → controller | Plan on the dashboard, from an idea, an issue or nothing. The controller creates branch `plan/<slug>` with the topic or issue in its git branch description, a worktree in `.claude/worktrees/`, and a planner session that starts with `/planner:plan`. | the plan process runs |
| Shape | planner + you | `/planner:grill` asks numbered question rounds along the decision tree; facts it looks up itself, decisions are yours. `/planner:research` and `/planner:prototype` settle what talking cannot. Then `/planner:spec` writes one `spec` issue. `/planner:tickets` cuts it into `ready-for-agent` sub-issues with native blocking edges, attached to the milestone you name (or none). For an existing issue, `/planner:triage` verifies, grills, posts the agent brief and sets the labels. Finish in the process view removes the worktree. | issues exist; the board shows them in the frontier |
| Claim | you → controller | Claim on the board, in manual or yolo mode. The controller refuses an issue that is not `ready-for-agent`, is routed to the factory, or whose branch is on origin; force lifts those refusals. It creates branch `feat/123-slug` and its worktree, assigns the issue to you and starts the implement session. | the work process runs |
| Implement | worker | A headless session with the `worker` agent reads the issue itself, implements, verifies with the single test or linter for the files it touched, and commits. It asks a question in the process view when it needs you. | the session reports complete |
| Gate | controller | Merges the base into the branch and runs the gate command (`WF_GATE`, `make check` by default) or hands it to CI through a draft pull request. A failure starts a fix session. | the gate passes |
| Review | controller + panel | The reviewers of `WF_REVIEWERS` run in parallel, each a fresh read-only session briefed with the diff, the issue and the gate's last run. A finding of `S1` or `S2` starts a fix session; a later round re-runs only the reviewers that said FIX. Max `WF_REVIEW_ROUNDS`. | every reviewer passes |
| PR | controller + author session | Pushes the branch; a read-only author session writes the title and body from the diff, the commits and the issue. The controller adds `Closes #123` and a verification section with the gate run and each reviewer's verdict. | the pull request is open |
| CI and external review | controller | Waits on the pull request: conflicts first, then the checks, then one review of `WF_PR_BOT_REVIEWERS` within `WF_PR_REVIEW_WAIT` seconds, then standing requests for changes and unresolved threads. A conflict or a failed check starts a repair session; a review that asks for changes starts an address-reviews session, which fixes or declines each point and replies. At most `WF_CI_REPAIR_ROUNDS` repair rounds. | green and `CLEAN` |
| Merge (manual) | you → controller | Merge on the board refuses unless checks pass, no changes are requested, and the merge state is `CLEAN`. Then it squash-merges, deletes the branch, and removes the worktree and the process. | merged |
| Merge (yolo) | controller | A yolo process merges itself by the same rules once the panel is ready and CI is green, then cleans up and closes the issue. | merged |
| Accept | planner + you | Once every ticket of a spec is closed, the board lists it and an acceptance start opens a plan process on it. `/planner:accept` prints the facts and lets one read-only `spec-checker` judge every checkable statement of the spec against the base. Per item that is not met you choose: a gap ticket, an accepted deviation recorded on the spec, or no finding. | spec closed as completed with the acceptance comment |
| Release | you → controller | Once every issue in a milestone is closed, release it. With `main` alone the controller tags the head of `main`. With `dev` it opens the promotion `chore(release): v1.2.0`, merges it when green with a merge commit, and tags that. Then it publishes the release with generated notes and closes the milestone. Never automatic. | released |

Parallelism: claim as many issues as you like and plan several topics at once. The board lists every project with its processes and their state, the frontier of claimable issues, and the specs due for an acceptance. A process that asks something is blocked: open its view and answer.

Recovery: the controller resumes its processes from its state when it restarts. A session opens in a terminal by its session id when the dashboard lacks something. Abandon removes a stuck worktree and its process, and refuses to delete unpushed work without force.

Per-repository variation: set `WF_REVIEWERS` and the other `WF_*` variables, and write what an agent must know into `AGENTS.md`. Repository-local skills, agents, commands and rules are not part of the [standard](repo-standard.md); the check fails on them.
